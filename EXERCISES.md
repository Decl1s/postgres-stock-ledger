# Пять упражнений с проверкой результата

Создай входы: `.venv/bin/python -m stock_ledger sample --output workspace/input`.
В Windows используй `.venv/Scripts/python.exe`. Каждый опыт с workshop сохраняй
в новую --output, чтобы предыдущий результат и правки остались для сравнения.

## 1. Изменить допустимый расход

В workspace/input/dispatch.csv замени E0004 BOOK -3 на -8.
Запусти workshop с receipts.csv и dispatch.csv по порядку.
Ожидается BAG=3, BOOK=2, PEN=16, 6 событий и 2 партии. Затем верни -3.
Найди разницу между количеством строк файла и вставленных событий: повтор E0002
уже принят первой партией. Он не является дополнительным приходом.

## 2. Доказать атомарный отказ

В dispatch.csv замени E0004 на расход -30. Другие движения оставь правильными.
Ожидается отказ всей второй партии: BAG=5, BOOK=10, PEN=20, 3 события, 1 партия.
Даже корректные расходы PEN/BAG не принимаются частично. Проверь шаг в steps.json
и найди запрос, после которого Python поднимает DataError. Верни -3.

## 3. Повтор и конфликт события

Добавь в dispatch.csv ещё одну точную E0005,PEN,-4. Итог остаётся 7/16/3,
входных строк второй партии станет 5, уникальных событий останется 4, вставленных — 3.
Теперь измени только эту добавленную копию на -5. Вся вторая партия должна
отклониться как конфликт staging. Объясни, почему ON CONFLICT DO NOTHING само
по себе скрыло бы эту проблему. Удали учебную дополнительную строку после опыта.

## 4. Добавить показатель прихода и расхода

Расширь snapshot: для каждого SKU верни received и dispatched как положительные
суммы, сохраняя quantity. Используй условные агрегаты SQL и добавь интеграционный тест.
Для исходных двух партий ожидаются BOOK 10/3/7, PEN 20/4/16, BAG 5/2/3.
received - dispatched должно равняться quantity. Не складывай дубли повторно.
Это изменение отчёта, а не самого журнала; пересоздание таблицы events не требуется.

## 5. Найти причину блокировки и выбрать развитие

Запусти интеграционный тест test_writer_waits_for_existing_transaction через отладчик.
Найди удерживающую транзакцию, worker и момент выхода из with. Не меняя глобальный
сервер, объясни, почему отчёт SELECT может читать, а второй писатель ждёт.
Автоматическая проверка требует, чтобы Future не завершился в первые 0.2 секунды,
а после освобождения вставил 3 события. Долгая пауза отладчика может дать lock timeout.

Дополнительный проектный вопрос: как дать разным SKU загружаться одновременно?
Сначала опиши отдельную таблицу остатков, порядок блокировки SKU, создание нового SKU
и откат вместе с журналом. Просто удалять глобальный LOCK нельзя: два независимых
списания могут по отдельности пройти проверку и вместе уйти в минус.
Проверка будущего решения — сохранить тест конкурирующих списаний и добавить
пример независимых SKU. В текущей версии такая оптимизация не реализована.
