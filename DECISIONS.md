# Обоснование решений

| Решение | Зачем | Цена и когда пересмотреть |
| --- | --- | --- |
| PostgreSQL 16.15 | Доступен в среде; настоящие транзакции, ограничения и конкурентные клиенты | Нужен серверный runtime; версия 16.x выбрана намеренно, не называется самой новой основной версией |
| Psycopg 3.3.6 с binary | COPY и транзакции без локальной C-сборки | Бинарная поставка содержит libpq; версии и платформенные зависимости закреплены в uv.lock |
| Журнал событий вместо изменяемой таблицы остатков | Повтор проверяется по event_id; остаток всегда выводится из принятых движений | SUM всей истории дорожает; далее возможна транзакционно поддерживаемая таблица остатков |
| Две таблицы batches/events | Различаем ключ загрузки и ключ бизнес-события | Схема длиннее одного INSERT, зато повтор файла не путается с повтором события в другом файле |
| Хэш исходных байтов | Тот же batch_id означает тот же вход, без догадок | CRLF/LF меняют ключ содержимого даже при тех же событиях; это контракт загрузки, не семантический хэш |
| Точный дубль и конфликт разделены | Нельзя скрывать E0001 с другим количеством через ON CONFLICT | Нужно два запроса в staging; UPDATE по конфликту здесь запрещён |
| COPY FROM STDIN | Данные передаются драйвером; серверу не нужны пути клиентской файловой системы | Весь небольшой CSV уже в памяти; для большого файла потребуется потоковый контракт |
| TEMP incoming ON COMMIT DROP | Изоляция staging между соединениями и автоматическая очистка | Это промежуточное состояние, оно не сохраняется для отдельного аудита плохого файла |
| Один COMMIT на партию | Ошибка остатка не оставляет частичного склада | Большой файл держит транзакцию/блокировку дольше; поэтому объём ограничен |
| SHARE ROW EXCLUSIVE на batches/events | Писатели упорядочены, проверка суммы не гоняется с другой загрузкой | Простой глобальный сериализатор, не вариант для высокой нагрузки. Следующий шаг — блокировки остатков отдельных SKU в одинаковом порядке |
| READ COMMITTED для загрузки | После ожидания блокировки следующий SELECT видит принятую предыдущую партию | Не заменяет саму блокировку. Удаление LOCK при той же проверке открывает гонку |
| REPEATABLE READ READ ONLY для отчёта | Несколько SELECT относятся к одному снимку | Отчёт может показывать состояние до недавнего COMMIT, но внутренне согласован |
| CHECK, PK и FK в БД | Ошибки формы и связей отклоняются независимо от Python | SUM по журналу не является CHECK одной строки; владелец базы может обойти приложение прямым SQL |
| Временный кластер со SCRAM | Демо автономно, чужая база не нужна, постоянная служба не создаётся | После выхода база исчезает. Для ручной долгой работы используй отдельную учебную STOCK_DSN |
| Никакого автоматического retry | Ошибки контракта требуют решения, а неизвестный исход COMMIT требует правильного ключа | Внешний повтор можно делать тем же batch_id/байтами; политику сетевых ошибок надо проектировать отдельно |
| unit отдельно от integration | Можно быстро проверить CSV на любой ОС, а транзакции доказать настоящей БД | Зелёные unit-тесты не подтверждают работу PostgreSQL; интеграция не пропускается молча |
| Явный PUBLIC_FILES.txt | Архив не захватывает CSV, PGDATA, пароль и чужие проекты | Новый исходник надо включить осознанно; поиск шаблонов не заменяет ревью безопасности |

SQL-файлы отвечают за структуру и массовые операции, Python — за управление
границей транзакции и контракт клиентского файла. Для трёх запросов ORM добавил
бы уровень абстракции, не убрав необходимость понимать SQL и блокировки.
База не требует отдельного индекса sku для текущего полного GROUP BY: PK event_id
обеспечивает проверку дублей, а ускорение аналитики стоит выбирать после измерений.

Новая семантика схемы требует версии, миграции и проверки совместимости. Изменение
pyproject.version само по себе не мигрирует базу. Прямой UPDATE старого события
не подходит модели неизменяемого журнала: исправление — новое компенсирующее движение.
